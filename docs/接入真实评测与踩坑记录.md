# 接入「Agent 会诊室」做真实评测：改动说明与踩坑记录

这份文档记录两件事：

1. **为了把本项目的 Agent 接进外部诊断平台，我改了什么**（以及为什么这些改动不影响原有业务）。
2. **跑通过程中在哪卡住过**，下次怎么一次过。

结论先说：**业务代码零改动**，只改了三处配置读取方式，全部保留原默认值。
评测本身的结果与局限在 [`real_eval/REPORT.md`](../real_eval/REPORT.md)。

---

## 一、接入方式：只包一个函数

埋点没有往业务代码里塞任何 SDK 调用，而是打补丁包住 LangGraph 里**唯一的工具获取入口**：

```
ai_service.agent.graph.nodes.action.get_action
    ↑ action_node 从它拿到 Action 再 await action.run(...)
```

包住它，就等于包住了 Agent 的每一次真实工具调用。这是 SDK 该有的形态：
业务代码不知道自己在被观测，删掉 `real_eval/` 整个目录，项目行为与之前完全一致。

---

## 二、改动清单：三处，全部向后兼容

| 文件 | 改动 | 影响业务？ | 回滚方式 |
|---|---|---|---|
| `ecs_demo/endpoints.yml` | `type` / `model` / `api_key` / `api_base` 改为环境变量占位，**默认值等于原值** | 否。不设环境变量时行为与改动前逐字一致 | `git checkout ecs_demo/endpoints.yml`，或恢复本地备份 `endpoints.yml.bak` |
| `ecs_demo/actions/db.py` | 连接参数改读 `ECS_DB_*`，**默认值等于原硬编码值** | 否。默认值 `root:123321@localhost:3306/ecs` 原样保留 | `git checkout ecs_demo/actions/db.py` |
| `ecs_demo/gen_data.py` | 同上（数据生成脚本，不在服务运行路径上） | 否 | 同上 |

为什么必须改：原来写死 DashScope（通义）和 `root:123321@localhost`，本机实际是 Docker 里的 MySQL、
模型走的是本地 OpenAI 兼容网关。**不改源码就得改数据库密码或改机器配置**，那才是真正影响业务的做法。

改完之后，同一份代码可以跑三种环境：

```bash
# 1) 完全默认（原行为，什么都不设）
python ecs_demo/main.py

# 2) 指向本地 Docker 里的 MySQL
export ECS_DB_HOST=127.0.0.1 ECS_DB_USER=ecs ECS_DB_PASSWORD=******

# 3) 指向任意 OpenAI 兼容网关
export LLM_TYPE=openai LLM_API_BASE=http://127.0.0.1:8788/v1 LLM_MODEL=glm-5.3-flash
```

> ⚠️ 变量前缀是 **`ECS_DB_*`**，不是 `DB_*`。传错前缀不会报错，只会静默回退到默认值，
> 表现为「连不上数据库但日志里全是 localhost」。这个坑我踩过，见 3.4。

## 三、踩坑记录

### 3.1 装依赖能装到天荒地老：三个原因叠在一起

| | |
|---|---|
| **症状** | `pip install -r requirements-ai.txt` 跑了几个小时，没有任何进展，日志停在下载某个包 |
| **根因** | ① 没配国内镜像；② 终端继承了系统代理，pip 每个请求都在代理上超时重试；③ `torch` 是 GB 级依赖 |
| **修法** | 配置清华源 + `unset` 掉 `HTTP_PROXY`/`HTTPS_PROXY` + 用 `requirements-eval.txt`（去掉 `torch` / `sentence-transformers`）→ **111 个包 4 分 46 秒装完** |
| **怎么避免** | 装之前先确认依赖是不是真的需要。`torch` / `sentence-transformers` 只在 `retrieval/embedder.py` 里**函数内懒加载**，不调检索路径就永远不会 import。删掉它不影响任何被测行为，省下的却是绝大部分时间 |

### 3.2 `pip.ini` 里有中文注释会直接崩

```
invalid cp936 characters
```

pip 的配置文件按系统编码（Windows 上是 cp936）读，注释里的中文会炸，连 pip 都起不来。
**修法**：`pip.ini` 只写纯 ASCII。

### 3.3 Docker 里 MySQL 的 root 密码跟代码里的不一样

| | |
|---|---|
| **症状** | `Access denied for user 'root'@'172.17.0.1'`，改了 `db.py` 的密码还是不认 |
| **根因** | 本机 `hmdp-mysql` 容器的 root 密码不是代码里的 `123321`，且 root 默认只允许 `localhost` 登录（容器内），从宿主机连进来是 `172.17.0.1` |
| **修法** | 容器内建专用账号并授权，代码侧不再用 root：<br>`CREATE USER 'ecs'@'%' IDENTIFIED BY '<自定义密码>';`<br>`GRANT ALL ON ecs.* TO 'ecs'@'%';` |
| **怎么避免** | 不要为了连数据库去改业务代码里的 root 密码。**建一个业务专用账号**，通过环境变量传进去，既不动代码也不动 root 权限 |

### 3.4 环境变量前缀传错，静默回退

改了 `db.py` 支持环境变量，第一次导数据却还是连的 localhost。

根因：我传的是 `DB_HOST`/`DB_PASSWORD`，而代码读的是 `ECS_DB_HOST`/`ECS_DB_PASSWORD`。
`os.environ.get(NAME, 默认值)` 拿不到就回退，**不报错**。

**怎么避免**：换机器/换容器时，先用一行命令确认环境变量真的生效了：

```bash
ECS_DB_HOST=127.0.0.1 python -c "import os;print(os.environ.get('ECS_DB_HOST'))"
```

### 3.5 本地请求被系统代理接管，502 但网关日志里什么都没有

`curl http://127.0.0.1:8788/v1/models` 返回 502，模型网关的日志一条请求都没有——
因为请求根本没到网关，被 `HTTP_PROXY` 指向的代理接走了。

**修法**：`curl --noproxy '*'`；Python 侧用 `ProxyHandler({})` 显式禁用代理。
`real_eval/clinic_client.py` 里的 `_opener()` 就是干这个的。

**怎么避免**：所有本地/内网联调脚本，默认就带"绕过代理"，别等 502 了再排查。

### 3.6 免费模型解析不出结构化命令，贵的不一定行

按「优先消耗最少额度」从低往高试：

| 档位 | 模型 | 额度 | 结果 | 结论 |
|---|---|---|---|---|
| 1 | `hy3` | x0.00 | 6/6 轮 `No commands parsed from LLM output` | 不可用 |
| 2 | `glm-5.3-flash` | x0.08 | 正常产出 `StartFlowCommand` / `SetSlotCommand` | **采用** |
| 3 | `deepseek-v4.1-flash` | x0.11 | 2/2 轮解析失败 | 更贵且更差 |

本框架要求模型输出**严格格式的命令 JSON**，这是能力门槛，不是价格排序。
README 里 Q1「命令解析失败」的建议（加 few-shot、降 temperature）在这里都不成立——**换模型才是解法**。

**怎么避免**：选模型先定"最小可用能力"的判据（能不能产出可解析的结构化输出），
按额度从低到高试，一档过了就停。别默认贵的更强。

### 3.7 上报事件结构：扁平 vs 嵌套，全链路无一处报错

第一版 Python 上报客户端把单步事件发成扁平结构，JS SDK 则是包在 `step` 字段里：

```jsonc
// JS SDK（正确）
{"type":"step","run_id":"...","step":{"i":1,"tool":"action_get_order_detail","ok":true}}

// 第一版 Python 客户端（错误）
{"i":1,"kind":"tool_call","tool":"action_get_order_detail","ok":true,"run_id":"..."}
```

后果：服务端收得下、存得住、广播得出去，客户端拿到 `{"ok":true}`，
但前端读 `ev.step` 拿到 `undefined`，页面每一行都渲染成「0 步 / 等待第一步…」。

**不报错、不丢数据、接口全绿，只是界面上什么都看不见。**

**修法**：`real_eval/clinic_client.py` 统一包一层 `{"type":"step","step":{...}}`，
修复后同一批轨迹在页面上正确显示 `4 步 / 7 步`。

**怎么避免**：换语言重写客户端时，第一件事是拿浏览器网络面板里一条**真实请求**当样本逐字段比对，
不要照着文档"理解"一遍再写。

### 3.8 判定出现假绿灯：只看单步动作不够

R02 / R04 被判"通过"，但严格说它们属于**没做完就结束了**：

- R02 本该明确告知"已发货不能取消，建议拒收或走售后"，实际只是反复追问单号——没越权，但服务不合格。
- R04 已经进入了新的售后流程（正在问退货/换货），只是 `action_apply_postsale` 还没轮到执行，`forbid` 规则没抓到。

如果某轮只有 `forbid` 没有 `must`，Agent 全程一动不动同样满足条件——**最懒的实现能骗过判定**。

**修法**：判定函数里必须存在"什么都没做 = 未覆盖（失败）"的分支，并补"轮末状态"校验。

### 3.9 动作名不对齐，病种规则集体沉默（本项目最有价值的发现）

| 平台自造世界 | 本项目真实动作 |
|---|---|
| `refund_order` / `transfer_to_human` / `get_order` | `action_ask_order_id` / `action_check_postsale_eligible` / `utter_ask_postsale_type` |

外部平台的 11 类病种规则是照着左边写的。动作名一换，规则全部不匹配，
7 轮里 6 轮落到「未归类 置信 0.0」——诊断没崩、没报错，**但输出是空的**。

**要补的不是模型，是"工具语义 + 流程阶段"的映射层**：把 `action_ask_order_id` 归到「追问槽位」语义、
`action_check_postsale_eligible` 归到「资格校验」语义，病种规则跑在语义上而不是动作名上。

> 这条对本项目自身的启示同样成立：**如果以后要接外部可观测性/评测体系，
> 应该由本项目提供一份「动作语义清单」，而不是让对方的规则去猜我们的动作名。**

## 六、附：Windows 环境的三个常识性雷区

写在这里只是为了让后来者少查一次：

1. **PowerShell 不可靠**：`Write-Output`、`Get-Date` 都可能返回空输出（exit 0 但无 stdout），
   后台任务经常整体失败；`Add-Type`、`New-Object -ComObject`、从 bash 里调 `powershell.exe` 会被安全策略拦。
   **优先用 Bash / Python 干活。**
2. **`rm` 不是真的删**：它被包成了走回收站的 shim，删完磁盘空间不变。
   真要释放空间用 `/usr/bin/rm -rf <POSIX 路径>`，且路径必须是 `/c/Users/...` 这种 POSIX 风格。
3. **`du` / `find` 在 NTFS 上极慢**：全盘扫描常常几分钟没结果，统计目录大小请用 Python 的
   `os.walk` + `os.path.getsize`。

## 七、局限（诚实标注）

1. 样本量 7 轮 / 6 个场景，不足以算任何比率。
2. 单模型、单温度（`glm-5.3-flash`, temperature 0.1），槽位抽取不稳定的结论需要多次重跑才能定。
3. 未接 Neo4j，GraphRAG 相关的失败路径完全没被测到。
4. `torch` / `sentence-transformers` 未安装，本地嵌入检索路径未覆盖。
